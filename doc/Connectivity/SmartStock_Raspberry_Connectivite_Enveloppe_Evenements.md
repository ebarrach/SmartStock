# SmartStock — Event envelope

*Raspberry Pi and connectivity · step 2*

> [Step 1 — architecture and tools](SmartStock_Raspberry_Connectivite.md) · **Step 2 — event envelope** · [Step 3 — reconnection and local queue](SmartStock_Raspberry_Connectivite_Reconnexion_File_Locale.md)

All messages exchanged between the bag, the cabinet (Raspberry Pi) and the phone share the same JSON envelope, regardless of the transport: HTTPS over Wi-Fi or BLE/GATT. The envelope only describes the **container**; the content of `data` depends on the type of event and other areas of the project.

## 1. Envelope structure

| Field | Role | Status |
| ---| ---| ---|
| `v` | Schema version: integer that starts at 1. Allows you to change the format without breaking clients. | Proposed |
| `id` | Unique event identifier (UUID v4), generated by the sender. Used to spot duplicates when resending. | Proposed |
| `type` | Nature of the event, in `domain.action` format (e.g. `stock.changed`, `ack`). | To be decided (list of types) |
| `src` | Identifier of the sender (e.g. `cabinet-01`, `bag-01`, `phone-01`). | Proposed |
| `seq` | Increasing counter specific to each sender: gives the order of messages and reveals gaps. | Proposed |
| `ts` | UTC timestamp in ISO 8601 format, set by the sender. | Proposed |
| `corr` | Identifier of the event to which we respond (case of an ack); `null` otherwise. | Proposed |
| `data` | Content specific to the event type (JSON object). | To be decided (schema per type) |

## 2. Examples

### Event emitted by the cabinet

```json
{
  "v": 1,
  "id": "7f3c2a9e-5b1d-4c8e-9a62-0d4e1f7b8c35",
  "type": "stock.changed",
  "src": "cabinet-01",
  "seq": 42,
  "ts": "2026-10-16T09:30:12Z",
  "corr": null,
  "data": {}
}
```

### Acknowledgment of receipt (ack) returned by the telephone

```json
{
  "v": 1,
  "id": "b2d94c10-3e7a-4f56-8c1b-95a0e6d2f741",
  "type": "ack",
  "src": "phone-01",
  "seq": 7,
  "ts": "2026-10-16T09:30:13Z",
  "corr": "7f3c2a9e-5b1d-4c8e-9a62-0d4e1f7b8c35",
  "data": { "status": "ok" }
}
```

## 3. Rules of transportation and operation

| Subject | Rule | Status |
| ---| ---| ---|
| Wi-Fi (cabinet ↔ telephone) | The envelope travels in JSON in HTTPS: sending an event, reading events from a given `seq`. The answer is ack. | Proposed (HTTP routes) |
| BLE (bag ↔ cabinet, phone) | Same logical envelope. A GATT characteristic in notification (bag to client) and one in writing (client to bag, for ack). | Proposed (UUID to freeze) |
| Message size in BLE | A JSON message exceeds the default payload of 20 bytes: the MTU must be negotiated and/or the message fragmented, or the format compacted. | Finding |
| Ack and resend | Every event expects an ack. Without ack it is resent with the same `id`. A duplicate received is ignored but acknowledged. | Proposed (delay, attempts) |
| Offline | The events are kept in a local queue of the Pi (pending or acknowledged) then replayed in the order of `seq` upon reconnection. | Proposed (detail: step 3) |
| Recovery after interruption | The client announces the last `seq` received per sender; the sender sends the rest. | Proposed |
| Pi Clock | Without internet on the local network, the Pi time may be wrong. The `seq` remains the order reference. | Proposed |
| Security | HTTPS on the Wi-Fi side (already planned). Pairing and encryption on the BLE side. | To be decided |
| Errors | The ack carries a status (`ok`, `duplicate`, `error`). All that remains to be defined are the error codes and the “unsupported version” case. | To be decided |
