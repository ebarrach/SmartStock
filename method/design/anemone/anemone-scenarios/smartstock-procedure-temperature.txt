============================================================
SMARTSTOCK — DÉMONSTRATION ANEMONE / TEMPÉRATURE
Scénario : la température simulée passe à 27.0 °C
============================================================

OBJECTIF
--------
Reconstruire manuellement dans Anemone le modèle réellement
exécuté par la Démo 02 de SmartStock Visualizer.

Une température simulée est publiée dans le Blackboard.
L'agent Anemone sélectionne cette température et applique ses
équations pour produire un terme ventilation(puissance).
Deux ventilateurs de l'interface illustrent ensuite la puissance.

SEUILS DE DÉMONSTRATION
Ce sont des paramètres pédagogiques configurables.
Ils ne constituent pas des recommandations médicales,
pharmaceutiques ou une certification de conservation de produits.

Le modèle actuel accepte 15.0 à 35.0 °C, au dixième de degré.
Les exemples sont des entrées simulées : aucun capteur physique
de température et aucun ventilateur matériel ne sont pilotés.

Ce document est autonome : les définitions à copier sont données
en entier. Ne soumettre au parseur que les blocs Anemone indiqués.
Les boutons GUI mentionnés proviennent des sources de l'installation.
Les résultats du moteur sont validés headless ; les manipulations
GUI décrites ci-dessous restent un tutoriel à suivre manuellement.


============================================================
ÉTAPE 1 — COMPRENDRE LE SCÉNARIO
============================================================

Le stockage est initialement représenté par une mesure de 23.0 °C.
Pour la démonstration principale, l'étudiant applique ensuite 27.0 °C.
On veut laisser Anemone produire :

    ventilation(75)

EXPLICATION POUR LE PROF :
"Nous simulons une mesure, mais la décision de ventilation du
mode Anemone provient réellement de l'agent et de ses équations.
Le navigateur anime une puissance reçue ; il ne la choisit pas."


============================================================
ÉTAPE 2 — COMPRENDRE LES TERMES
============================================================

L'atome t270 signifie 270 dixièmes, donc 27.0 °C.
Ce n'est pas une variable et ce n'est pas le nombre décimal 27.0.
Le préfixe t permet une représentation discrète explicite.

    t150 -> 15.0 °C
    t200 -> 20.0 °C
    t230 -> 23.0 °C
    t250 -> 25.0 °C
    t270 -> 27.0 °C
    t300 -> 30.0 °C
    t350 -> 35.0 °C

Termes employés :

temperature(t270)
    Mesure d'entrée à traiter. Elle sera consommée par get.

temperature_current(t270)
    Mesure traitée conservée par l'agent dans le store.

fan(t270)
    Expression à simplifier avec les équations Anemone.
    Il ne s'agit pas d'un nouveau terme publié seul dans le store.

ventilation(75)
    Sortie de décision publiée par le moteur.
    75 est une puissance en pourcentage, pas une température.

q
    Variable de l'agent, instanciée parmi les membres de Temperatures.

Préparer un Current store vide, sans agent ancien en cours.
Clear vide le store mais ne retire pas les définitions.

La GUI autonome utilise son propre Blackboard.
Elle n'affiche pas la session headless du Visualizer.
Ne pas mélanger ces deux processus pour vérifier un même état.

ÉTAPE 5 — REPRODUIRE L'ÉTAT INITIAL DE L'APPLICATION
============================================================

Dans si-term, écrire :

temperature(t230)

Multiplicity : 1
Cliquer : Tell.

Current store :

    temperature(t230) [1]

À ce stade, aucune ventilation n'a été décidée.
Dans l'application, fanPower est null, pas une valeur inventée.
Si l'on exécutait l'agent sur cette mesure, il produirait 25 %.
Pour le scénario principal, nous allons remplacer la mesure par 27 °C.

Puis publier :

    si-term : temperature(t270)
    multiplicity : 1
    bouton : Tell

BLACKBOARD AVANT EXÉCUTION :

Une seule entrée température doit être présente.
Ne pas conserver plusieurs mesures concurrentes : le sum
pourrait sélectionner une autre branche exécutable.

Dans le Visualizer, APPLIQUER TEMPÉRATURE remplace les anciens

ÉTAPE 7 — CRÉER LE VÉRITABLE AGENT TEMPÉRATURE
============================================================

    get(temperature(q));

    tell(ventilation(fan(q)))


============================================================
ÉTAPE 8 — EXPLIQUER L'AGENT INSTRUCTION PAR INSTRUCTION
============================================================

1. sum q in Temperatures:
   Le moteur construit les instances possibles de l'agent.
   Les valeurs vont de t150 à t350, pas de 150 à 350 °C.
   sum est un choix généralisé, pas une addition.

2. get(temperature(q))
   Avec temperature(t270) présent, la branche q=t270 peut réussir.
   Le moteur consomme cette entrée et conserve cette continuation.

3. tell(temperature_current(q))
   Le moteur publie la mesure traitée : temperature_current(t270).

4. tell(ventilation(fan(q)))
   La continuation contient fan(t270).
   La simplification consulte les équations chargées.
   fan(t270)=75 donne le terme final ventilation(75).

Il n'y a pas de test JavaScript ou Java du type
"température >= 28 donc 100" dans le chemin du mode réel.
La table est préparée à l'avance comme des équations Anemone.


============================================================
ÉTAPE 9 — EXÉCUTER ET OBSERVER LES QUATRE PAS
============================================================

Cliquer Run pour terminer le scénario.
Ou utiliser le bouton Next de la GUI pour observer un pas à la fois.
Dans le Visualizer, le bouton correspondant est PAS À PAS.

PAS 1 — DÉVELOPPEMENT DU CHOIX
    Blackboard : temperature(t270) [1]
    Agent restant : choix développé sur Temperatures.
    La mesure n'est pas encore consommée.

PAS 2 — CONSOMMATION DE LA MESURE
    Blackboard : VIDE.
    Agent restant :
    tell(temperature_current(t270));tell(ventilation(fan(t270)))

PAS 3 — PUBLICATION DE LA MESURE TRAITÉE
    Blackboard : temperature_current(t270) [1]
    Agent restant EXACT :
    tell(ventilation(fan(t270)))

PAS 4 — RÉSOLUTION ET PUBLICATION DE LA VENTILATION
    Blackboard :
    temperature_current(t270) [1]
    ventilation(75) [1]
    Agent terminé.

Ces quatre étapes proviennent des exécutions du vrai moteur.
Le store n'a pas d'ordre d'affichage garanti.
Le journal de l'application conserve les observations de ces pas ;
il ne réintroduit pas la mesure consommée dans le Blackboard actuel.


============================================================
ÉTAPE 10 — EXEMPLES AVEC PLUSIEURS TEMPÉRATURES
============================================================

Valeurs de la séquence automatique effectivement configurée :

    20.0 °C -> t200 -> fan(t200)=0   -> ventilation(0)
    23.0 °C -> t230 -> fan(t230)=25  -> ventilation(25)
    25.0 °C -> t250 -> fan(t250)=50  -> ventilation(50)
    27.0 °C -> t270 -> fan(t270)=75  -> ventilation(75)
    30.0 °C -> t300 -> fan(t300)=100 -> ventilation(100)
    24.0 °C -> t240 -> fan(t240)=50  -> ventilation(50)

Pour un deuxième essai MANUEL après le premier essai à 27 °C :
1. L'agent doit être terminé.
2. Retirer temperature_current(t270) avec Get, multiplicité 1.
3. Retirer ventilation(75) avec Get, multiplicité 1.
4. Publier temperature(t200) avec Tell, multiplicité 1.
5. Soumettre de nouveau le même texte d'agent avec Submit.
6. Exécuter Run ou quatre Next.
7. Vérifier temperature_current(t200) [1], ventilation(0) [1].

Cela reste la même instance de Blackboard.
Les anciennes sorties sont retirées avant la nouvelle mesure.
Ne pas publier soi-même ventilation(0) : c'est le résultat à observer.

Dans le Visualizer : appliquer la nouvelle température puis RUN.
Le Bridge réalise le nettoyage des anciens termes ; il ne publie
aucune nouvelle puissance. La décision revient à l'agent.


============================================================
ÉTAPE 11 — SEUILS PÉDAGOGIQUES ET BORNES
============================================================

    15.0 <= température < 22.0 :   0 %
    22.0 <= température < 24.0 :  25 %
    24.0 <= température < 26.0 :  50 %
    26.0 <= température < 28.0 :  75 %
    28.0 <= température <=35.0 : 100 %

Exemples de bornes vérifiés :
    21.9 °C -> 0 % ; 22.0 °C -> 25 %
    23.9 °C -> 25 % ; 24.0 °C -> 50 %
    27.9 °C -> 75 % ; 28.0 °C -> 100 %

La discrétisation par dixièmes évite de supposer un calcul
flottant ou une comparaison numérique non vérifiée dans Anemone.
Chaque valeur autorisée possède sa propre équation explicite.


============================================================
ÉTAPE 12 — VISUALISATION DES VENTILATEURS
============================================================

Le Visualizer lit le terme ventilation(...) dans le vrai store,
expose fanPower dans le JSON et anime les deux ventilateurs.

    0 %   : arrêt
    25 %  : lent
    50 %  : moyen
    75 %  : rapide
    100 % : très rapide

Les transitions de vitesse sont interpolées graphiquement.
Ce calcul d'angle/vitesse est une animation, pas la règle métier.
Le mode de réduction des animations du navigateur peut désactiver
la rotation ; la puissance numérique reste affichée.

Anemone autonome ne dessine pas ces ventilateurs web.
La GUI permet de vérifier les termes ; le Visualizer les illustre.


============================================================
INTÉGRATION AVEC LE BRIDGE JAVA
============================================================

Configuration centrale : config/temperature-policy.json.
Préparation des définitions :
    node experiments/generate-temperature-scenario.mjs

Ce script écrit les équations Anemone, les métadonnées de contrôle
et les paramètres d'affichage/Demo. Il ne tourne pas pour chaque
requête et n'exécute pas la régulation réelle à la place d'Anemone.

Fichiers exécutés :
    anemone-scenarios/temperature/definitions.anemone
    anemone-scenarios/temperature/regulation.anemone
    anemone-scenarios/temperature/metadata.properties

TemperatureEngineSession possède son ABBlackboard persistant,
séparé de la session de stock. Les définitions sont chargées par
AnimBachSimulParser puis addDecls/addEqns.

APPLIQUER transmet la mesure via POST /api/temperature/apply?value=27.0.
Java valide et encode le dixième, puis fait tell(temperature(t270)).
RUN/PAS À PAS utilisent ABSimulExec.run_one sur le vrai AST.
La puissance est lue dans le terme ventilation du store, pas déduite
de la température dans Java. HTTP/SSE transmettent les observations.

Le Diagnostic moteur montre les 201 équations chargées, l'ensemble,
le moteur instancié et les AST avant/après le dernier run_one.


============================================================
MODE ANEMONE / MODE DEMO / LIMITES
============================================================

MODE ANEMONE :
    entrée de température simulée ; décision par le vrai moteur.
    Un Bridge indisponible provoque une erreur visible.

MODE DEMO :
    résultats et journal simulés par TemperatureDemoDataSource.
    Fonctionne sans Bridge et porte le bandeau DONNÉES SIMULÉES.
    La séquence automatique n'est pas une preuve d'exécution Anemone.

LIMITES :
    seuils pédagogiques, sans norme médicale revendiquée ;
    plage finie et pas de 0.1 °C ;
    pas de capteur ni de ventilateur physique ;
    nouvelle entrée refusée pendant une exécution ou une pause ;
    une session persistante en mémoire, perdue à l'arrêt JVM ;
    RESET recrée explicitement la session à 23.0 °C sans décider
    d'une puissance avant l'exécution de l'agent.

Après modification de la politique, régénérer puis redémarrer.
Le bloc de ce document correspond à la configuration présente lors
de sa rédaction. Si la politique change, mettre aussi ce tutoriel
à jour et vérifier les tests ; ne pas conserver un guide contradictoire.
